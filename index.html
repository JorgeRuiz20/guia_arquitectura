Fundamento Primordial

1. ¿Qué es una Arquitectura en Backend?

No es simplemente "dónde pongo mis archivos", sino el conjunto de decisiones estructurales de más alto nivel que definen responsabilidades, límites de comunicación y reglas de dependencia para que el sistema sobreviva al tiempo.

🏛️

La Analogía del Rascacielos

Cualquiera puede clavar cuatro tablas y armar una choza en el patio, pero para levantar una torre de 40 pisos necesitas planos de cargas, cimientos antisísmicos, ductos de cableado aislados y rutas de evacuación. La arquitectura es ese plano que evita que el sistema colapse cuando aumenta el tráfico.

Estructura Cimientos Límites
🎯

Separación de Incumbencias (SoC)

Cada componente debe tener una única razón para cambiar (Principio SRP). La capa web no debe saber de sentencias SQL, y las reglas del negocio no deben preocuparse si la petición provino de un navegador, un bot o un cron job.

SoC Desacoplamiento SOLID
🔄

Inversión de Dependencias (DIP)

Los módulos de alto nivel (el negocio) no deben depender de los módulos de bajo nivel (bases de datos, frameworks, APIs externas). Ambos deben depender de abstracciones e interfaces bien delimitadas.

Interfaces Contratos Independencia

Impacto Real: Código Espagueti vs Arquitectura Desacoplada

⚠️ Código Espagueti (Sin Arquitectura)

  • Controladores con 1,500 líneas haciendo consultas SQL directas y validaciones.
  • Si cambias el nombre de una columna en la base de datos, se rompe el frontend y el servicio de correos.
  • Escribir pruebas automatizadas es casi imposible sin encender una base de datos real.
  • Nuevos programadores tardan semanas en entender dónde colocar una nueva función.
  • El "Miedo a tocar el código": arreglas un bug en facturación y se cae el login.

✅ Arquitectura Limpia & Desacoplada

  • Controlador ligero (~30 líneas): solo recibe HTTP, valida sintaxis y delega al caso de uso.
  • Puedes cambiar PostgreSQL por DynamoDB sin alterar una sola línea de lógica de negocio.
  • Pruebas unitarias que se ejecutan en 40 milisegundos usando mocks de interfaces.
  • Estructura intuitiva y predecible: cada archivo tiene un rol claro y delimitado.
  • El negocio evoluciona rápidamente sin efectos colaterales imprevistos.

3. Tipos de Arquitectura Backend al Detalle

Aquí analizamos cada patrón con visión de Arquitecto Senior: su árbol real de carpetas, qué tiene permitido y prohibido importar cada capa, cómo viajan los datos internamente y las trampas comunes de juniors.

1. Arquitectura en Capas Tradicional (N-Tier / Layered)

Es la arquitectura más extendida en la industria para comenzar proyectos web. Organiza el código en estratos horizontales superpuestos, donde cada estrato solo ofrece servicios a la capa inmediatamente superior.

src/main/java/com/jorge/tienda/
├── controller/ // Capa Web / Entrada HTTP
│ ├── UserController.java // Expone @PostMapping, valida @Valid
│ └── OrderController.java
├── dto/ // Objetos de Transferencia de Datos
│ ├── request/ // CreateUserRequestDTO.java
│ └── response/ // UserResponseDTO.java (¡Sin passwords!)
├── service/ // Capa de Negocio
│ ├── UserService.java // Interfaz con los contratos del servicio
│ └── impl/ // UserServiceImpl.java (Lógica real, @Transactional)
├── repository/ // Capa de Acceso a Datos
│ └── UserRepository.java // Hereda de JpaRepository<UserEntity, Long>
├── entity/ // Modelo de Persistencia Relacional
│ └── UserEntity.java // Mapeo a tabla de BD (@Entity, @Table)
└── exception/ // Manejo Global
└── GlobalExceptionHandler.java // @RestControllerAdvice
Capa Responsabilidad Única Tiene Permitido Importar Tiene PROHIBIDO Importar
Controller Recibir solicitud HTTP, autenticar cabeceras, validar sintaxis con DTO y devolver código de estado HTTP (200, 201, 400). Service DTOs 🚫 Repositories 🚫 Entidades JPA 🚫 Consultas SQL
Service Orquestar casos de uso, aplicar cálculos de negocio, verificar unicidad de datos y controlar transacciones (@Transactional). Repository Entities Mappers 🚫 HttpServletRequest 🚫 Clases de UI 🚫 Generar JSON
Repository Consultar, persistir, actualizar y eliminar registros en la base de datos a través de JDBC u ORM. Entities Spring Data / ORM 🚫 Reglas de negocio 🚫 DTOs de Controller 🚫 HTTP
Entity Representar la estructura física de la tabla en base de datos (columnas, llaves foráneas, índices). Jakarta Persistence 🚫 Servicios 🚫 Repositorios 🚫 Controllers
1
Petición entrante al Controller: El cliente envía POST /users con JSON. El Controller recibe y valida automáticamente el CreateUserRequestDTO. Si falta el email, aborta de inmediato con 400 Bad Request.
2
Llamada al Service: El Controller llama a userService.createUser(dto). El Controller nunca hace SQL ni sabe en qué base de datos se guarda.
3
Ejecución en Service & Creación de Entity: El Service verifica que el email no esté repetido consultando userRepository.existsByEmail(). Hashea la contraseña y transforma los datos en un UserEntity.
4
Persistencia en Repository & BD: El Service ejecuta userRepository.save(entity). El ORM genera el INSERT INTO users ... y la base de datos asigna el ID.
5
Retorno Sanitizado: El Service toma la entidad persistida, la mapea a un UserResponseDTO (sin password) y se la entrega al Controller, quien responde con HTTP 201 Created.

💡 Visión de Arquitecto Senior: La Trampa de la "Arquitectura Dirigida por Base de Datos"

En la arquitectura en capas tradicional, la dirección de las dependencias fluye Controller ➔ Service ➔ Repository ➔ Base de Datos.

El Gran Defecto: Todo el sistema tiende a acoplarse al modelo de la base de datos. Si una columna cambia de nombre en SQL, la Entidad cambia, lo que obliga a cambiar el Service y potencialmente el Controller.

Regla de Oro Senior: Usa siempre DTOs independientes y Mappers. Nunca expongas la entidad de base de datos directamente en el Controller. Si tu negocio empieza a tener más de 20 reglas complejas, migra este monolito hacia Arquitectura Hexagonal antes de que los servicios se conviertan en "God Classes".

2. Arquitectura Hexagonal (Ports & Adapters - Cockburn)

Diseñada para aislar radicalmente las reglas de negocio del mundo exterior. Tu aplicación se divide en un Núcleo de Dominio puro rodeado por Puertos (Interfaces) y Adaptadores intercambiables.

src/main/java/com/jorge/hexagonal/
├── domain/ // 🏛️ NÚCLEO PURO (¡Cero dependencias de librerías!)
│ ├── model/ // User.java, Email.java, Money.java
│ └── exception/ // InsufficientBalanceException.java
├── application/ // Casos de Uso y Contratos
│ ├── ports/
│ │ ├── input/ // CreateUserUseCase.java (Interfaz hacia el mundo exterior)
│ │ └── output/ // UserRepositoryPort.java, NotificationPort.java
│ └── service/ // CreateUserService.java (Implementa CreateUserUseCase)
└── infrastructure/ // Herramientas, BD, APIs y Frameworks
└── adapters/
├── input/ // Quienes inician acciones
│ ├── rest/ // UserRestController.java, UserRequestDto.java
│ └── messaging/ // RabbitMQOrderListener.java
└── output/ // Quienes ejecutan hacia afuera
├── persistence/ // PostgresUserAdapter.java, UserJpaEntity.java
└── email/ // SendGridEmailAdapter.java
Estrato Responsabilidad Permitido Importar TERMINANTEMENTE PROHIBIDO
Domain Modelar entidades puras, invariantes de negocio y reglas que existirían incluso si no existieran computadoras ni internet. Java/TS Estándar 🚫 Spring Boot 🚫 JPA/Hibernate 🚫 HTTP/Jackson
Application (Ports & Services) Definir qué puede hacer el sistema (Puertos de Entrada) y qué herramientas externas necesita (Puertos de Salida). Domain 🚫 Postgres Driver 🚫 Controladores REST 🚫 SQL
Infrastructure (Adapters) Traducir el mundo técnico exterior hacia los puertos de la aplicación y viceversa. Application Domain Spring/JPA/Kafka 🚫 Alterar reglas del dominio sin pasar por un caso de uso
1
Adaptador de Entrada (Driver Adapter): El cliente hace HTTP POST. El UserRestController (Adaptador Primario) recibe la llamada, valida y traduce el JSON a un objeto del Dominio.
2
Cruza el Puerto de Entrada (Inbound Port): El controlador invoca la interfaz CreateUserUseCase.execute(user) sin saber qué clase concreta lo ejecutará.
3
Servicio de Aplicación en el Núcleo: CreateUserService procesa la lógica de negocio pura. Cuando necesita persistir los datos, no llama a una base de datos directamente, sino al Puerto de Salida UserRepositoryPort.save(user).
4
Adaptador de Salida (Driven Adapter) en Infraestructura: La clase PostgresUserAdapter implementa el UserRepositoryPort. Toma el modelo puro User, lo mapea a UserJpaEntity y ejecuta el SQL en PostgreSQL.
5
Retorno de Datos Desacoplado: La BD confirma la inserción, el adaptador devuelve el User de dominio al caso de uso, y el caso de uso devuelve al controlador, quien responde en formato JSON.

💡 Visión de Arquitecto Senior: La Magia de la Inversión de Dependencias (DIP)

¿Por qué Hexagonal es tan potente? Observa el truco arquitectónico:

Flujo de Control (En tiempo de ejecución): El código corre de izquierda a derecha: Controller ➔ Caso de Uso ➔ Adaptador de BD.
Flujo de Dependencias (En tiempo de compilación): ¡Va hacia adentro! La base de datos DEPENDE del Puerto declarado por la Aplicación. El núcleo del negocio no tiene idea de qué motor de base de datos se utiliza.

Beneficio Senior Inmediato: Para escribir pruebas unitarias de tus casos de uso, no necesitas bases de datos en memoria (H2) ni contenedores Docker. Simplemente creas un MockUserRepository en memoria y los tests corren en 5 milisegundos.

3. Clean Architecture (Onion / Robert C. Martin)

Se basa en la Regla de Dependencia Concéntrica: Las capas internas NUNCA pueden saber nada de las capas externas. Los frameworks, la web y las bases de datos son meros detalles secundarios reemplazables.

src/main/java/com/jorge/clean/
├── domain/ // Círculo 1: Entidades Empresariales Puras
│ ├── User.java // Reglas críticas del negocio independiente de la app
│ └── Money.java
├── usecase/ // Círculo 2: Reglas de Aplicación
│ ├── RegisterUserInputBoundary.java // Interfaz de Entrada
│ ├── RegisterUserOutputBoundary.java // Interfaz de Salida (Presenter)
│ ├── RegisterUserInteractor.java // El Caso de Uso orquestador
│ └── RegisterUserRequestModel.java // Datos puros para el caso de uso
├── adapter/ // Círculo 3: Adaptadores de Interfaces
│ ├── controller/ // UserController.java
│ ├── presenter/ // UserWebPresenter.java (Prepara ViewModel)
│ └── gateway/ // UserDataGateway.java (Interfaz para persistencia)
└── framework/ // Círculo 4: Frameworks & Drivers
├── web/ // Configuración de Servidor, Spring Security
└── database/ // JPA Repositories, Migraciones Flyway
Círculo Concéntrico Componente Hacia dónde apuntan sus dependencias Regla Fundamental
Centro (1) Enterprise Entities Hacia nadie Si la empresa cambia de web a una app de escritorio, las entidades no sufren ninguna modificación.
Medio (2) Application Use Cases Hacia el Centro (Entities) Orquesta los flujos de datos hacia y desde las entidades. Solo usa Request/Response Models.
Intermedio (3) Interface Adapters Hacia los Use Cases y Entities Convierte datos del formato conveniente para los casos de uso al formato conveniente para la web/BD.
Exterior (4) Frameworks & Drivers Hacia los Adapters Aquí viven las bibliotecas de terceros, Postgres, AWS SDK, Spring. Es la capa más volátil.
1
Controller empaqueta el RequestModel: El UserController recibe la petición web, la transforma en RegisterUserRequestModel e invoca a RegisterUserInputBoundary.execute(requestModel).
2
El Interactor aplica el Caso de Uso: RegisterUserInteractor toma los datos, instancia la Entity User pura y ejecuta los métodos de negocio.
3
Persistencia vía Gateway: El interactor invoca la interfaz UserDataGateway.save(user). La implementación en el círculo externo persiste en base de datos.
4
El Salto al Presenter (Output Boundary): En lugar de que el caso de uso le devuelva un valor directo al Controller, el interactor llama a RegisterUserOutputBoundary.present(responseModel).
5
Generación del ViewModel: El UserWebPresenter recibe el ResponseModel, formatea fechas o monedas para la vista web y entrega el UserViewModel al cliente.

💡 Visión de Arquitecto Senior: ¿Cuándo Clean Architecture se vuelve Sobreingeniería?

Clean Architecture es una de las arquitecturas más robustas jamás concebidas, pero tiene un precio: muchas clases intermedias (RequestModel, ResponseModel, InputBoundary, OutputBoundary, Interactor, Presenter, ViewModel).

Advertencia Senior: Si tu aplicación es un CRUD simple con poca lógica de negocio, implementar Clean Architecture completa te generará hasta 8 archivos por cada endpoint trivial. Aplícala cuando las reglas de negocio sean complejas, cambien con frecuencia o cuando tengas múltiples interfaces (Web, CLI, Móvil, Batch) consumiendo el mismo núcleo.

4. Arquitectura de Microservicios Distribuidos

Descompone un sistema grande en múltiples servicios pequeños e independientes divididos por dominios de negocio (Bounded Contexts), donde cada servicio es dueño exclusivo de su propia base de datos.

enterprise-ecosystem/
├── api-gateway/ // Enrutamiento, SSL, Rate Limit, Auth JWT
├── auth-service/ // Servicio de Identidad & OAuth2 (PostgreSQL propia)
├── order-service/ // Gestión de Pedidos (MongoDB propia)
│ ├── src/main/java/com/jorge/orders/
│ │ ├── controller/ // POST /orders
│ │ ├── client/ // PaymentFeignClient.java (Llamada HTTP síncrona con Circuit Breaker)
│ │ └── event/ // OrderCreatedEventPublisher.java (Kafka)
│ └── Dockerfile
├── payment-service/ // Pagos y pasarelas bancarias (MySQL propia)
├── notification-service/ // Consumidor asíncrono de eventos (Push, Email)
└── k8s/ // Manifiestos Kubernetes, Helm charts e Istio Service Mesh
Principio Significado Práctico Beneficio Consecuencia si se Rompe
Database per Service Ningún servicio puede hacer SELECT ni JOIN directo a la base de datos de otro servicio. Despliegues y cambios de esquema sin coordinar con otros equipos. Acoplamiento letal en BD
API Contract First La comunicación entre servicios se rige por contratos estrictos (OpenAPI o Protobuf gRPC). Compatibilidad hacia atrás con versionado (v1, v2). Roturas masivas en producción
Fallas Aisladas Si el servicio de Notificaciones colapsa, los usuarios aún deben poder comprar órdenes. Resiliencia mediante Circuit Breakers (Resilience4j). Caída en cascada de todo el ecosistema
1
API Gateway Intercepta: El usuario llama a POST /orders. El Gateway valida el token JWT, aplica rate-limiting y redirige la petición al clúster de order-service.
2
Transacción Local en Order Service: order-service crea la orden con estado PENDING y la guarda en su propia base de datos (Transacción ACID local de 15ms).
3
Publicación de Evento (Patrón SAGA): El servicio de pedidos emite el evento OrderCreatedEvent { orderId: 105, total: $80 } hacia el broker Apache Kafka.
4
Consumo Asíncrono en Payment Service: payment-service lee el evento, procesa el cargo con Stripe o PayPal y publica un nuevo evento: PaymentCapturedEvent.
5
Consistencia Eventual Completada: order-service escucha PaymentCapturedEvent y actualiza el estado de la orden a CONFIRMED. Paralelamente, notification-service envía el email de confirmación.

💡 Visión de Arquitecto Senior: La Trampa del "Monolito Distribuido"

Muchos equipos saltan a microservicios creyendo que solucionará sus problemas de organización, y terminan creando lo peor de ambos mundos:

El Monolito Distribuido ocurre cuando: Tus microservicios se llaman síncronamente por HTTP en cascada (A llama a B, B llama a C, C llama a D). Si C se cae o tarda 2 segundos, A colapsa. Además, comparten la misma base de datos relacional.

Recomendación Senior Innegociable: Comienza siempre con un Monolito Modular bien diseñado. Divide primero por módulos con interfaces limpias en un solo repositorio. Solo divide en microservicios cuando un módulo específico requiera escalar de forma extrema o cuando tengas más de 25 ingenieros divididos en squads autónomos.

5. Arquitectura Dirigida por Eventos (EDA)

En lugar del paradigma clásico donde un cliente espera bloqueado a que el servidor termine todo, en EDA los sistemas reaccionan a hechos consumados en el pasado (Eventos) de forma totalmente asíncrona.

src/main/java/com/jorge/eda/
├── producer/ // Emisor de Eventos
│ ├── UserRegisteredEventPublisher.java // Envía al Broker (Kafka/RabbitMQ)
│ └── OutboxRelayScheduler.java // Garantía de entrega transaccional
├── consumer/ // Suscriptores en Paralelo
│ ├── WelcomeEmailConsumer.java // Escucha "user.registered" ➔ envía correo
│ ├── AnalyticsTrackingConsumer.java // Registra en Data Lake
│ └── AuditSecurityConsumer.java // Auditoría de cumplimiento
└── schema/ // Contrato del Evento (Avro / JSON Schema)
└── UserRegisteredEvent.java // Contiene eventId, timestamp, correlationId
Elemento Regla de Diseño Por qué es Vital
Inmutabilidad del Evento Un evento es un hecho que YA OCURRIÓ (en tiempo pasado: OrderCreated, no CreateOrder). Jamás puede modificarse. Permite tener una pista de auditoría perfecta y reejecutar eventos si es necesario.
Desacoplamiento del Productor El productor publica al broker y se desentiende. No sabe cuántos consumidores existen ni si están despiertos. Si el servicio de analítica está caído, el checkout de compras sigue funcionando al 100%.
Esquema Estricto Los campos del evento deben tener compatibilidad hacia atrás mediante un Schema Registry. Evita que un productor nuevo rompa a los consumidores antiguos que están en producción.
1
Ocurrencia y Publicación: El usuario Jorge se registra. El backend persiste al usuario en DB y publica de inmediato el paquete UserRegisteredEvent con un eventId único al tópico de Kafka users.events.
2
Distribución en el Broker: Kafka almacena el evento en su log inmutable y asigna un offset secuencial persistido en disco replicado en 3 nodos.
3
Procesamiento en Paralelo: Tres servicios totalmente independientes leen el mismo evento en simultáneo: EmailService prepara el saludo, AnalyticsService calcula métricas y FraudService revisa la IP.
4
Manejo de Errores con Dead Letter Queue (DLQ): Si el servicio de email falla tras 3 reintentos automáticos, el mensaje no se pierde; se envía al tópico users.events.DLQ para ser inspeccionado por soporte.

💡 Visión de Arquitecto Senior: Idempotencia y el Patrón Transactional Outbox

En sistemas basados en eventos, la red NO es perfecta. Los brokers garantizan entrega "At-least-once" (al menos una vez), lo que significa que un evento puede llegar duplicado.

Regla Senior 1 (Idempotencia Obligatoria): Tus consumidores SIEMPRE deben ser idempotentes. Antes de procesar, verifica en Redis o en tu BD si el eventId ya fue procesado: if (processedEvents.contains(event.id)) return;.

Regla Senior 2 (Transactional Outbox): Nunca hagas un userRepository.save(user) y en la línea siguiente kafkaTemplate.send(event). Si la base de datos comitea pero la red hacia Kafka se cae, el evento nunca se publicará. El Patrón Outbox guarda el evento en una tabla outbox_events dentro de la misma transacción ACID de la BD y un proceso en segundo plano lo envía a Kafka de forma 100% infalible.

6. CQRS (Command Query Responsibility Segregation)

Separa radicalmente el camino de escritura de datos (Commands) del camino de lectura de datos (Queries), permitiendo optimizar cada modelo de forma 100% independiente.

src/main/java/com/jorge/cqrs/
├── command/ // ✍️ CAMINO DE ESCRITURA (Mutaciones / Estado)
│ ├── CreateOrderCommand.java // Intención de modificar estado
│ ├── CreateOrderCommandHandler.java // Valida reglas pesadas de negocio
│ └── OrderWriteRepository.java // Escribe en BD Relacional normalizada
├── query/ // 📖 CAMINO DE LECTURA (Cero lógica de negocio, ultra rápido)
│ ├── GetOrderSummaryQuery.java // Parámetros de búsqueda
│ ├── GetOrderSummaryQueryHandler.java // Consulta directa a lectura
│ ├── OrderReadModelDTO.java // DTO plano desnormalizado
│ └── OrderReadRepository.java // Lee de Elasticsearch o MongoDB
└── projection/ // 🔄 Sincronizador de Escritura ➔ Lectura
└── OrderProjectionHandler.java // Actualiza el modelo de lectura tras cada evento
Concepto Commands (Escritura) Queries (Lectura)
Intención Modificar estado (Crear, Editar, Pagar, Cancelar). Consultar información sin alterar absolutamente nada.
Retorno de Datos Retorna éxito/fracaso o el ID generado. No debe retornar datos complejos. Retorna un DTO optimizado listo para que el frontend lo dibuje en pantalla.
Base de Datos Ideal BD Relacional Normalizada (Postgres) para evitar redundancias y asegurar integridad. BD Desnormalizada o Cache (Elasticsearch, Read Replicas, Redis, Mongo).
Carga Típica Baja/Media (ej: 5% del tráfico total). Muy Alta (ej: 95% del tráfico total: búsquedas, catálogos).
1
Flujo de Escritura (Command): El usuario crea una orden. Se envía un CreateOrderCommand. El CommandHandler valida stock y dinero, genera la transacción de escritura en PostgreSQL y emite OrderCreatedEvent.
2
Proyección Asíncrona: Un ProjectionHandler escucha el evento y precalcula una vista desnormalizada en una base de datos optimizada para lectura (ej. MongoDB o vista SQL con todos los datos ya unidos, sin necesidad de hacer 6 JOINs).
3
Flujo de Lectura (Query): Cuando un cliente o panel de administración consulta el resumen de la orden, llama al QueryHandler, el cual hace un simple SELECT directo a la vista precalculada en 3 milisegundos sin tocar el modelo de dominio ni la base de datos de escritura.

💡 Visión de Arquitecto Senior: El Gran Poder y el Riesgo de la Consistencia Eventual

En la mayoría de los sistemas, los usuarios consultan datos 100 veces más de lo que escriben. CQRS resuelve esto de raíz porque puedes tener 1 nodo de escritura y 15 réplicas de lectura rápida.

El Desafío Senior: Entre que el Command escribe en PostgreSQL y la proyección actualiza la base de datos de lectura, pasan unos 50 a 300 milisegundos. Si el usuario recarga la página inmediatamente, podría no ver su orden de inmediato. Esto se maneja con Optimistic UI en el frontend o notificando vía WebSockets cuando la proyección esté lista.
